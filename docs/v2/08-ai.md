# 08 — AI assistant

The assistant edits the design through the **same operations layer as the UI** (05). The model proposes
operations; core validates and applies them; the user gets one undo step per request.

## Flow

```
Browser                                   Server  /api/ai/turn (streaming, SSE)
 message + doc + doc.revision + history ─►  validate request (schema, size, origin)
                                            loop (≤ 8 model calls):
                                              model call (provider adapter, streamed)
                                              ◄ text deltas ─────────────────► forwarded to browser as they arrive
                                              tool calls → core.applyTransaction(scratchDoc, ops, partial)
                                              tool results (applied / clamped / errors) → model
 ◄── final: { transaction (applied ops, ids filled in), changes[], reply, history, baseRevision }
browser: rebase transaction onto current doc (05) → commit as one undo step, or report a conflict
```

- The server applies ops to a **scratch copy** only to validate and to give the model accurate feedback
  (new ids, clamped values). The browser owns the real document and commits the returned transaction. The
  transaction is `ApplyResult.applied` (05): every created id is in the ops, so the browser's replay (with
  `noNewIds`) creates the same ids the model was told about.
- History (provider-native messages) stays in the browser and is sent back each turn, **append-only**
  (assistant content is echoed unchanged — thinking blocks must not be edited or reordered).
- The current design is attached to each user message as compact JSON (entities with ids, sizes, world
  bounds, columns/items/fronts summaries) — not the whole parts list.

## Tools

One tool, `apply_operations`, whose input schema is generated from the op schema (05) with each
template's param schema inlined. Its description and the system prompt are generated from the catalog
(templates, categories, param labels, limits) — adding a template updates the AI automatically.

Tool results always answer every tool call:
- unknown tool name → error result naming the only tool;
- reply cut off at `max_tokens` → error result "not applied, send fewer operations";
- invalid input → per-op errors with the schema path and message.

## Providers

```ts
interface ProviderAdapter {
  stream(history, system, tools, signal): AsyncIterable<ProviderEvent>;  // text deltas, tool calls, stop
  userMessage(text): unknown[];
  toolResults(results): unknown[];
}
```

### Anthropic (default)

- Official SDK `@anthropic-ai/sdk`, model **`claude-opus-5-5`** by default (user-selectable).
- Streaming (`client.messages.stream`, final message via `finalMessage()`), `max_tokens` 64 000.
- `output_config.effort`: `medium` by default (set explicitly; user-selectable), sent only to models that accept it.
- Thinking: leave adaptive (omit the parameter); do not send `budget_tokens` or `disabled` (rejected on current models).
- **No forced `tool_choice`** (`any`/`tool` are rejected on current models); steer via the prompt.
- Client tools stream with `eager_input_streaming: true`; validate every parsed tool input with zod
  before applying (partial/truncated input is possible) and check `stop_reason` (`max_tokens`, `refusal`)
  before running tools.
- Server-side refusal fallback on by default for models that support it: beta
  `server-side-fallback-2026-07-01` with `fallbacks: "default"`; `stop_reason: "refusal"` on the final
  response is shown as "the model declined this request".
- Errors mapped with the SDK's typed classes (authentication, permission, not found, rate limit, bad request,
  connection) to readable messages.

### OpenAI-compatible

- `POST {baseUrl}/chat/completions` with `tools` (function calling), streamed when the server supports it.
- Robust to local servers: tool-call ids may be missing (generate and echo them); arguments may arrive as an
  object instead of a JSON string; invalid JSON → error tool result.
- Tested against Ollama, LM Studio and mlx-serve (e.g. `http://localhost:11234/v1`,
  `lmstudio-community/Qwen3.8-27B-MLX-4bit`).

## Security (all enforced server-side, all tested)

1. **Keys never reach the browser.** `GET /api/ai/config` reports only whether keys exist.
2. **A server key is only sent to its configured endpoint**: `ANTHROPIC_API_KEY` → Anthropic's default URL;
   `LLM_API_KEY` → `LLM_BASE_URL`. A browser-chosen base URL requires a key typed by that user. For
   Anthropic with a custom URL and no typed key, refuse before constructing the SDK client (the SDK would
   otherwise pick up environment credentials on its own).
3. **No cross-site use**: require `Content-Type: application/json` (forces CORS preflight) and an `Origin`
   equal to the server's host; reject otherwise (403/415).
4. **Bounded requests**: body ≤ 4 MB; message ≤ 10 000 chars; history ≤ 400 entries / 3 MB (reject with
   "start a new chat" — never silently drop history, it must stay append-only); ≤ 8 model calls per turn.
5. **Optional access token** for LAN use: `AI_ACCESS_TOKEN` env; the browser sends it from settings.
6. Provider error bodies are truncated (≤ 300 chars) before being shown.

## UI

- Chat panel (lazy-loaded) beside the properties panel; streamed reply text; change list per turn with
  "Undo this" (undoes that transaction if it is the latest, otherwise explains).
- Settings: provider, model, base URL, key (stored in this browser only), effort. Locked while a turn runs.
- "New chat" clears history; switching provider starts a new chat (histories are provider-specific).
- If the user edits during a turn and rebase fails, nothing is applied; the next user message is prefixed
  with a note telling the model its last changes were not applied.

## Tests

- Agent loop with a scripted fake provider: apply, error feedback, unknown tools, cut-off replies, refusal, step limit.
- Adapters: request shape (model, tools, no `tool_choice`, effort gating, fallback beta) and response mapping.
- Security: env key never sent to a browser-chosen URL; cross-site requests rejected; limits enforced.
- E2E: mock OpenAI-compatible server in the test → real browser → design changes → one undo step.
